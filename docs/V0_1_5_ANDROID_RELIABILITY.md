# v0.1.5 Android background reliability — test and handoff

**Primary target:** stock Android. GrapheneOS is optional compatibility testing. No OS-specific behavior is required.

## Runtime behavior

- Native `BOOT_COMPLETED` (after first unlock) and `MY_PACKAGE_REPLACED` handlers restore **only** explicitly saved background publication/following. Android may refuse a background foreground-service start; no permission bypass, auto-launch of the UI or resurrection of temporary previews.
- The native service and Activity use the persistent receiver ownership fence to prevent simultaneous writers. A receiver-only service must not request the location foreground-service type merely because a foreground-only share remains in storage.
- Network callbacks and Doze exit trigger the sender transport recovery and receiver re-dial. A separate periodic receiver check handles disconnected saved peers, with a 120-second retry floor. This cannot guarantee continuous delivery during Doze or while the app is force-stopped.
- An app-private, redacted Android journal keeps up to 14 UTC days, capped at 4 MB/day; browser/UI log keeps the newest 40,000 entries. Share logs exports both. No raw locations, addresses, tokens, identities or peer names are journaled. Optional per-peer 24-hour received-message trace remains **off by default**.

## Received-history diagnosis (0.1.5)

Reported symptom: the peer header and Connection details disagreed, while **Received messages** showed zero until a later app session revealed previously recorded events. The root cause on installed phones has not yet been proven. Three code paths were found and repaired:

1. The header summarized the best status from all incoming links, whereas the detail summary used the first link. Both now describe the same link; per-link details remain independent when a peer has multiple grants.
2. Service-owned follows previously mixed native counters/status with stale Activity timestamps and trace. The background receiver now owns all live fields as a unit. A missing service snapshot displays **checking background receiver**, not the false claim of zero recorded events. Opening the history inspector requests a fresh native status and foreground service recovery.
3. A receiver-only device had no outgoing shares, so returning the app to the foreground did **not** restart a stopped native service. Its persisted background-following ownership now triggers a bounded foreground restore. A persisted, opted-in location trace also supplies a historical last sender fix after process restart, without pretending the link is currently live.

Journal triage: `follow.received` reports the native runtime's aggregate number of decrypted observations; `follow.history.status` reports how many of those were retained in the opted-in trace; `sharing.background.history` in the foreground UI log reports its observed native generation, recorded-event total, and received count. Compare the timelines from both phones. If native recorded events increase while the UI remains empty, suspect the UI bridge/refresh. If received observations increase but recorded events do not, check opt-in propagation. The peer's `Last location` timestamp uses the sender's capture time; history rows use the receiver's arrival time. These timestamps can differ without implying a dropped message. No history is retroactively created before opt-in.

## v0.1.5 user-flow acceptance

- **Background following preference** defaults to `on` on Android, independently of native receiver ownership. It is **durably saved in Android encrypted private storage before** the asynchronous receiver start/stop handoff; a stop failure does not erase the opt-out and a stale ownership fence cannot restart an opted-out receiver. A one-time migration preserves the previous WebView-only opt-out on first visible startup. Missing or unreadable native intent prevents unattended receiver recovery until the app can safely resolve it. The UI displays saved intent independently from receiver running status and provides a warning if applying the policy fails. Test off/on, peer-count changes, owner handoff, storage failure, WebView reload, app update, reboot, OS force-stop and standby on physical devices.
- **Share back** opens the normal creation dialog with the original sender fixed as the only recipient. The sender chooses a nickname, location precision and duration (default: approximate for one hour) and explicitly confirms before a recipient-bound return grant is created. Canceling creates no share or offer. The peer widget closes when the form opens; after submission, a waiting card can be dismissed without revoking the grant. The card disappears only after authenticated return-recipient connection, not merely after the offer is queued. Failed creation keeps the dialog and draft for retry. A failed direct offer reports an error and leaves the already created private link available for manual delivery; it does not silently claim acceptance. Verify two independent senders, cancellation, chosen settings, failed storage, late acceptance and dismiss-before-acceptance; physical Android ownership handoff is still outstanding.
- **Nickname on each share:** Every new link (including explicitly confirmed return shares) receives a fresh randomly generated default nickname. The full share dialog shows an editable name and dice generator, with a help popup explaining that all recipients of one link see the same nickname, but separate links get separate names. There is no name-disclosure checkbox; the create button requires a non-empty nickname. Names are not device identity or authentication. A sender sees the exact nickname sent on each link in Connection details; recipients see the exact initial link nickname there too. A peer-level accepted name from an earlier link must not overwrite a later link's nickname; private labels and explicit reuse across reciprocal shares remain separate. Test two simultaneous viewers on one link, multiple links with the same sender, persistence across reopen, and name-help focus restoration.
- **Received messages** is the only UI location with the optional history-recording toggle (24 hours, off by default). Connection details retains a button to open history and count display but not another control. Color selector for incoming follows is in the top directional summary; duplicate top-level Manage link and Show on map buttons are removed. Test reciprocal shares with multiple links to verify each palette affects only its corresponding follow.

## Persisted preference versus effective Android fallback

- **Outgoing background sharing, battery interval, and network policy:** Always editable. Android saves the _requested_ behavior in encrypted app-private storage separately from the currently executing native policy. Without background location and notification grants, native shares use **foreground-only** execution; if device Location or foreground Location permission is off, **no GPS updates** are emitted. Saving cannot grant permission or authorize a viewer. A change to Android permission state re-applies the saved choice. The settings UI shows the missing grants and exact fallback, and retains in-progress draft edits while asynchronous permissions are rechecked.
- **Background following:** The encrypted native preference is the sole source of durable intent; the WebView key is migration-only. Receiver ownership and current status are independent operational observations, not alternative settings. A denied notification permission prevents unattended receiver restoration without modifying the preference. A stopped/failed receiver does not change the preference; turning it off and crashing before native stop acknowledgment must not restart it at boot.
- **Map cache/style and decluttering:** Saved independently of rendering capabilities. Grouping sub-options and thresholds remain editable with grouping off; disabled grouping falls back to individual markers. Local storage failures visibly say the setting lasts only for the current session.
- **Safety exceptions:** Explicit viewer approval, recording to an unsaved temporary preview, erasing data, and starting diagnostics are not generic user settings and retain their validity/consent guards. Android foreground-service startup and OS permission restrictions can still prevent execution. Physical Android acceptance must cover opt-out during stop failure and reboot, permission revoke/grant, background outgoing mode resynchronization, and app updates.

## 0.1.5 research — battery and OS power conditions

Android can defer or terminate background work under low battery, Battery Saver, Doze, application standby/restriction, Low Power Standby, network Data Saver, OEM-specific policies and process pressure. Treat these as hypotheses until a recorded state transition or Android `ApplicationExitInfo` correlates with a specific service stop. Do Not Disturb normally controls notification interruption, not continuous foreground-service eligibility. A vendor Bedtime or Sleep schedule may not be available to third-party apps: **do not infer one** from clock time, dark mode, or DND.

**Implemented initial telemetry:** `DevicePowerDiagnostics.kt` records battery percentage, Android low-battery flag, charging/plugged, background Data Saver status, notification interruption filter, app standby bucket, interactive screen state, and Low Power Standby (when available), alongside existing service heartbeat Doze, Battery Saver, battery-optimization-exempt, app-background-restricted, network and work-owner fields. It writes a privacy-safe snapshot at native service creation and on the five-minute heartbeat. Unsupported/unreadable fields are `unknown` or `unsupported`; it does not add any new permission, coordinates, peer identifiers or links. A five-minute heartbeat **cannot** catch a power event after an abrupt process kill; the prior exit reason and Android system diagnostic export remain necessary.

**Event-driven snapshots:** native battery-low/okay, charging connect/disconnect, Battery Saver, DND interruption-filter and screen on/off broadcasts, plus Data Saver and Doze changes, also write `service.power.changed`. These are bounded by system event frequency and do not wake a killed process. A missing event is not proof the mode was never enabled.

**Acceptance/research matrix (open):** compare unplugged normal, below 15% battery and critical-low battery; while charging; Battery Saver toggled; screen off/Doze and overnight stationary sleep; Data Saver on metered networks; Low Power Standby where supported; app battery restriction/unrestriction; DND on/off and OEM Bedtime settings; permission withdrawal; simulated process kill; boot and package replacement. Record which background share/follow operations actually stop versus simply delay messages. Keep the other device's journal as an independent witness. Repeat at least two overnight physical-device tests and compare actual OS process-exit reasons, last recorded battery snapshot, service restart policy and explicit stop/failure events. Do not change the app's power-optimization settings automatically.

**Known limitation:** Battery Saver, Doze and network restrictions already had heartbeat fields; the new fields improve correlation, not reliability by themselves. Android versions and OEMs differ, and Bedtime status may be unobservable.

## 0.1.5 — last known peer presence (implemented; field validation pending)

A saved follow retains its latest **authenticated, disclosed** location even when its P2P connection drops or the app restarts. One minimal snapshot (center, precision/radius, source sequence and original `capturedAt`/`expiresAt`) lives inside the existing encrypted private state. Heading, speed and altitude are not retained. No additional plaintext location cache or movement history is created. Preview-only links are not stored.

**Visual policy:** during the first two hours after the fix was captured, the existing identicon gradually fades to **45% opacity** but remains visible. After two hours, keep the identicon at 45% opacity with a small **clock badge**, plus an accessible `Last known · 3h 12m ago` label. All single, grouped, large-area and offscreen peer avatars use the same presentation; a minute clock updates labels without requiring network activity. A new authenticated fix immediately returns the marker to normal. Display the last _disclosed area_ and its original uncertainty, never a guessed exact coordinate or movement direction. Expiry of an individual observation makes it historical, not a new position.

**Retention policy:** retain the single snapshot only while its saved follow remains locally authorized. An infinite-duration follow can consequently retain its last fix indefinitely until the user stops following; that is a privacy trade-off of always preserving the map position. Stop/delete, explicit revocation, expiration, denied/renewed approval and invalid restored links clear the snapshot. Historical fixes are never republished. The 24-hour opt-in received-message trace is separate. Last-fix persistence is immediate on the first fix and batched to a 15-second interval thereafter to limit flash writes; an abrupt power loss can lose the most recent batch.

**Verification:** `src/sharing/lastKnownPersistence.test.ts` covers encrypted single-fix restore and stop cleanup; `src/location/lastKnownMarker.test.ts` covers fade/clock/expiry and own-marker exclusions; `tests/last-known-marker.spec.ts` covers visual badge/accessibility and fresh-fix transition on desktop and mobile. Android background viewer uses the existing encrypted receiver ownership fence and preserved `followed` field. Release-candidate field validation remains: long disconnection, app/service restart and reboot, revocation/expiry while offline, device screen sizes, group/radius panels, and battery-managed overnight behavior.
