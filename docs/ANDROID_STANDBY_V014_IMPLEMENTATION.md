# Android standby reliability — v0.1.4 implementation status

## Decisions and release gate

Both `android-incoming-background-reliability` and `android-sender-standby-transport-recovery` remain **planned** release blockers until device evidence confirms them. Product decision: best-effort P2P, bounded automatic recovery, accurate stale/policy status; one off-by-default global **Keep following in background** switch for saved subscriptions; versioned authenticated observation acknowledgement. No claim of delivery during OS-imposed Doze network suspension.

## Implemented: sender-side protocol and recovery foundations

- `src/sharing/shareProtocol.ts`: Constellation sharing v3 (`/constellation/location-share/3.0.0`) adds optional `receipt` to the authenticated `share.heartbeat` request. v2 remains supported; the viewer negotiates v3 first, then v2. Taskyon's generic sensor protocol is unchanged.
- `src/sharing/deliveryReceipt.ts`: immutable bounded pending-observation ledger (16), exact observation validation and monotonic confirmation; rejected, duplicate, or unknown receipts cannot improve delivery status.
- `src/sharing/sharingHelpers.ts`, `sharingViewerApi.ts`, `sharingContracts.ts`, `sharingProjection.ts`: receiver emits latest accepted/decrypted observation metadata only via v3 heartbeat; sender matches against actual session submissions; diagnostics separate local observation, submitted-to-P2P, confirmed-by-viewer, and unsupported older peers. No location coordinates or bearer secrets in receipts.
- `src/android/backgroundRuntimePolicy.ts`, `backgroundEntry.ts`, `sharingLifecycleApi.ts`, `LocationShareService.kt`: native network changes and Doze exit request rate-limited source reconnection, using one coalesced operation that restarts existing source nodes without changing share identities. A protected-WebView watchdog checks unacknowledged v3 observations independently of GPS fixes (90-second stall threshold, 5-minute retry floor), and suppresses retries while native reports no network. Does not request battery exemptions or imply guaranteed Doze operation.
- `src/components/NetworkDiagnosticsSheet.vue`: shows submission/receipt freshness without revealing peer IDs or network addresses unless explicitly requested.

## Implemented: opt-in Android receiver foundation (API 36 emulator verified; physical device pending)

- `src/sharing/followOwnership.ts`, `sharingLifecycleApi.ts`, `sharingViewerApi.ts`: serialized Activity/service ownership handoff; Activity viewer leaves sessions without revoking saved links, waits for outstanding protected writes, prevents foreground dials during service ownership, and restores saved follow state before resuming. Native start failures attempt cleanup; a failed release does **not** reopen an Activity viewer.
- `src-tauri/plugins/constellation-android/android/src/main/java/space/taskyon/constellation/plugin/ReceiverOwnershipFence.kt`: original Android Keystore identity/alias and durable owner/generation fence preserved. During service ownership, native encrypted JSON field-level merges let the Activity update source/UI records while only the service updates `followed`, `oldSeeing`, `pendingStopNotices`, and `pendingReturns`; stale generations or changed identity fail closed. The service cannot overwrite source keys, and source writes cannot erase saved subscriptions.
- `src/android/backgroundViewer.ts`, `backgroundEntry.ts`: service WebView runtime uses the existing libp2p/crypto viewer with the original identity, loads only saved-subscription fields, and never restores outgoing source shares. Generation-scoped native state bridge. No bearer URLs/keys in the receiver status projection; revoked, expired, denied and unsaved entries are excluded.
- `ConstellationAndroidPlugin.kt`, `LocationShareService.kt`, `src-tauri/plugins/constellation-android/src/mobile.rs`, `src-tauri/src/lib.rs`: native receiver commands and ownership status. Service keeps an explicit foreground notification and supports separate “Stop background following”. Restart restoration honors the persisted owner fence. The service does **not** claim uninterrupted delivery through OS Doze/network restrictions.
- `src/components/SettingsSheet.vue`, `src/views/MapView.vue`, `src/android/backgroundReceiver.ts`: single Android-only, off-by-default “Keep following in background” switch. Activity reconciles native ownership after foregrounding, displays live/stale received observations from service state, and blocks unsafe subscription writes until Activity ownership returns. Native status validates the generation and observation payloads before display.
- `src-tauri/plugins/constellation-android/android/src/main/AndroidManifest.xml`, `src-tauri/gen/android/app/src/main/AndroidManifest.xml`: proposed `specialUse` foreground-service type and permission alongside existing `location` for outgoing shares. This is **subject to Google Play declaration and review**, not approved by virtue of the manifest.

### Focused emulator standby soak (manual, not release acceptance)

The optional `--standby-soak-minutes=N` test uses an explicitly acknowledged **Until stopped** synthetic sharing link; the normal 1-hour test link would expire before the end of an overnight check. The runner puts an Android receiver into screen-off forced idle, does **not** probe or wake the device during the requested duration, and prints redacted host-only heartbeat markers every five minutes. After Doze exit it requires a fresh received observation, the original receiver ownership generation, and a safe native Stop/handoff. No real coordinates or invitation URLs appear in soak markers. Delivery **during** Doze is not required or claimed.

Run on the persistent sandbox host with an existing local-relay x86_64 debug APK:

```sh
env ANDROID_HOME=/android-state/sdk ANDROID_SDK_ROOT=/android-state/sdk \
  JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 \
  PATH=/android-state/bin:"$PATH" \
  ANDROID_AVD_HOME=/android-state/avd ANDROID_EMULATOR_HOME=/android-state/emulator \
  corepack yarn test:android:managed --receiver-standby-smoke \
  --standby-soak-minutes=480 --skip-build
```

`480` is eight hours; the command must stay attached to a persistent host/session. A suspended or destroyed sandbox/ADB/emulator invalidates the run. `--standby-soak-minutes=0.1` and `--standby-soak-minutes=1` both **passed** the full one-emulator receiver scenario on 2026-11-04, including native ownership preservation, a fresh post-Doze received observation, and safe Stop handoff. **No eight-hour run has been completed.** A second variant, `--two-android-receiver-standby-smoke --standby-soak-minutes=480`, checks both locked Android peers and additionally requires a fresh authenticated v3 acknowledgement from the receiver; it passed end to end on 2026-11-11 with a one-minute soak after two earlier setup attempts had failed before entering the soak (one ADB `error: closed`, one WebView/native-save evaluation timeout). The eight-hour duration and physical/OEM evidence remain unproven. An eight-hour two-device attempt that started on 2026-11-11 finished at minute 475 with no heartbeat gap, then the WebView debugger stalled on the post-soak read (`Runtime.evaluate` without a reply) and the acceptance checks never ran, so that run is not eight-hour evidence. The harness now reconnects the debugger and retries read-only evaluations once after a timeout or disconnect; state-changing evaluations still fail without a retry.

The emulator soak is narrower than physical overnight acceptance: it tests recovery **after** a sustained forced-idle period with a local relay, not intermittent wakeups, real cellular/Wi-Fi migration, OEM battery policies, or guaranteed live delivery while idle. Keep both v0.1.4 release blockers open.

## Physical-device handoff (pending real-world evidence)

1. Install the debug-signed ARM64 APK on an expendable device or isolated Android profile. **Do not uninstall/replace a production-signed app if preserving its local identity or data matters**; a different signing certificate cannot upgrade it.
2. Use two devices: one sender grants foreground/background location and creates a share; the receiver uses the saved link, enables **Keep following in background**, and should not require local location permission. Check notification visibility and the UI's live/stale indicators.
3. Compare last fix, last submitted observation, last authenticated receipt, and last viewed update while both devices are active; then repeat after 15–30 minutes locked, forced idle, Wi-Fi ↔ mobile-data migration, Data Saver, a blocked network, and an overnight standby cycle. A fix without a new authenticated receipt is **not** proof of delivery.
4. Test sender and receiver independently, plus both roles on one device. On the receiver, check the notification's **Stop background following** action, foreground handoff and saved subscriptions; try permission withdrawal, relaunch and OEM battery restrictions. Distinguish OS force-stop (no automatic restart promised) from ordinary process eviction.
5. Capture redacted time-series diagnostics and failure stage; never include coordinates, invite bearer links, encryption keys, or peer identifiers. Reproduce any failure with a focused emulator regression before marking the gate complete.
